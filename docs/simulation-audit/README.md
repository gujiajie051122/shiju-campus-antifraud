# 情境模拟功能核查

**后续已修正**：本页保留修改前的问题记录。当前实现和复测见 [role-update.md](role-update.md)。

核查日期：2026-11-17。目标：本地运行的 `/simulation`，当前版本。本轮只核查，没有修改产品逻辑。

## 结论

聊天可以连续收发，也能按话题选择不同回复；但目前没有实现核心的“AI 持续扮演诈骗方、根据用户表现动态推进虚构诈骗情境”。现有机制更接近由模型选择预设答案的教学对话。

## 实际验证

浏览器连续发送了岗位/工资/工时问题、工资详情追问、缺钱且担心被骗的问题，并查看培训费附件。消息与附件操作正常，等待回复时发送按钮禁用，回复完成后恢复。工资详情追问只重复原有句子，没有展开说明。担心被骗时，联系人主动提示自行核实、可以暂停，角色转成教学助手。

接口另测六组输入，原始结果见 `live-branches.json`：

| 输入情形 | 返回方式 | 观察 |
| --- | --- | --- |
| 同时询问工作、工资、工时 | model，5.3秒 | 覆盖三个话题，但均为固定句子 |
| 愿意交298元，问下一步 | model，18.0秒 | 混入“你可以先暂停”，与用户意图不一致 |
| 钱不够，想先开始工作 | rules，18.0秒 | 降级为预设回复，只回答工作内容，漏掉核心问题 |
| 明确拒绝交钱、退出 | rules，0.02秒 | 接受停止，符合退出处理预期 |
| 询问软件安装与共享 | model，17.5秒 | 仅复述通知要求 |
| 查到联系人未授权、流程不一致后质疑 | model，14.5秒 | 主动承认矛盾并指导暂停办理，诈骗方角色未保持 |

六次返回全部由固定菜单文字构成，其中四次由模型选菜单，两次走规则回复。`engine=model` 只能证明模型参与选择，不能证明回复正文由模型自然生成。耗时是本次本地实测值，不代表长期性能统计。

## 代码依据

- `app/simulation/page.tsx` 当前入口使用 `JobWorkshop`，核查的是当前招聘会话流程。
- `lib/job-dialogue.ts` 要求模型只输出 1–4 个 `replyIds`；最终正文由 `jobTurnReply` 拼接预设话术。
- `lib/job-conversation.ts` 通过规则、最近历史和引用定位话题，再合并模型选择；并非完整的诈骗情境阶段管理。
- `lib/job-workshop.ts` 的话术包含“自行通过公开渠道核实”“可以先暂停”等教学表达。部分菜单组合存在语义冲突。

引导演练设置了培训费情境；独立挑战设置了未经授权联系人、私发软件与屏幕共享情境。风险素材存在，但对话没有持续体现相应角色。虚构材料与操作不产生真实付款、下载或安装，应保留这一边界。

## 已通过的技术检查及其边界

运行 `tests/job-turn.test.mjs`、`tests/job-history.test.mjs`、`tests/job-workshop.test.mjs`、`tests/guest-budget.test.mjs`，共29项通过。它们验证会话分支、历史处理、材料和访客额度等现有机制，不验证诈骗方角色真实性；不能据此认定核心演练目标已达成。

## 建议修正顺序

1. 分离角色：聊天中由虚构诈骗方回应；知识提示与复盘在独立区域展示，避免角色主动讲解识破自己的方法。
2. 建立情境阶段与用户状态：区分了解岗位、建立信任、出现风险要求、犹豫、核实、识破、退出；同一问题的追问要能结合前文展开。
3. 在虚构设定和事实约束内生成自然回复，替代单纯选择固定段落；避免真实收款目标、真实软件安装和敏感信息收集。明确拒绝或退出后停止推进。
4. 增加行为验收：覆盖愿意继续、犹豫、提出异议、核验矛盾、重复追问、退出等连续多轮路径，检查相关性、角色一致性、事实一致性和响应时长。
